1. Project Description

MangaID is a self-hosted web application that translates any online manga, manhwa, or manhua chapter into natural Indonesian.

The user pastes a chapter link from any website (MangaDex, a scanlation site, a webtoon-style reader, etc.). The system detects and collects the chapter's page images, uses Google Gemini (multimodal) to read the original text, translates the whole chapter with consistent character names and tone, removes the original text from the artwork, and typesets the Indonesian translation inside the speech bubbles. The finished chapter is presented in a clean, MangaDex-style reader where the user can read it directly in the browser or download it as a PDF.

1.1 Problem Statement

  • Many titles have no Indonesian translation.
  • Existing workflows are manual and fragmented (download images → OCR → translate → clean → typeset), requiring technical skill and hours of work per chapter.
  • Existing translation tools are usually tied to specific sources or require local GPU-heavy setups.

1.2 Solution Summary

A single-input workflow — paste link → review detected pages → translate → read/download — powered entirely by Gemini for all AI tasks (text detection, OCR, language detection, translation), combined with free open-source image-processing libraries for cleaning and typesetting.

1.3 Goals

  • G1: Works with any public chapter URL through a layered, source-agnostic ingestion strategy.
  • G2: Natural, casual, context-consistent Indonesian translation (names, terms, tone).
  • G3: Automatic source-language detection (Japanese, Korean, Chinese, English, others).
  • G4: MangaDex-quality reading experience, mobile-first.
  • G5: PDF export of translated chapters.
  • G6: Operates within free-tier constraints (free tools, Gemini API free quota).

1.4 Non-Goals (v1)

  • User accounts, payments, comments, or social features.
  • Public hosting or distribution of translated content.
  • Bypassing logins, paywalls, DRM, CAPTCHAs, or anti-bot protections.
  • Perfect handling of stylized SFX or artistic lettering (best effort).
  • Native mobile apps.
  • Online hosting/deployment: v1 is local-only (runs on the owner's machine).

1.5 Target User

Indonesian readers who want to read titles unavailable in Indonesian, for personal, non-commercial use.

2. User Stories

  • U1: I paste any chapter URL and click "Analisis Halaman".
  • U2: I see thumbnails of the detected pages, and can remove, reorder, or add pages before translating.
  • U3: I click "Terjemahkan" and watch real-time progress (stage and page X of Y).
  • U4: I read the translated chapter in vertical-scroll mode.
  • U5: I toggle between Original and Translated.
  • U6: I download the translated chapter as a PDF.
  • U7: If a link cannot be processed automatically, I can upload images, a ZIP/CBZ, or a PDF instead.
  • U8: I retry only failed pages instead of re-running the whole chapter.
  • U9: I choose tone (gaul by default, aku/kamu, or neutral), honorific handling, and SFX handling.

4. Functional Requirements

FR-1 Universal Source Ingestion (CORE REQUIREMENT)

The system must accept an arbitrary URL and attempt to obtain the ordered list of chapter page images using a layered strategy. Each layer is tried in order; the pipeline moves to the next layer only if the previous layer fails or yields low confidence.

Define a SourceAdapter interface:

can_handle(url) -> bool
fetch_chapter(url) -> ChapterData(title, chapter_number, language_hint, page_image_urls, headers_needed)

Layer 0 — Known-site adapters (optional optimization). Dedicated adapters for sites with official/clean APIs (initially MangaDex via its official public API). Adapters are plugins; adding one must not require changes to core code. This layer is an optimization only — the system must remain fully functional without it.

Layer 1 — Generic static extraction. Fetch HTML with httpx (browser-like headers, polite User-Agent, timeouts, redirects) and parse with BeautifulSoup/lxml:

  • Collect candidate images from <img src>, data-src, data-lazy-src, data-original, srcset, <noscript> fallbacks, <picture>, and image URLs embedded in inline JSON/script tags.
  • Resolve relative URLs; send correct Referer/Origin headers when downloading images (hotlink protection).
  • Score and filter candidates: discard logos, avatars, ads, icons, and thumbnails using size (probe via HEAD or partial download), aspect ratio, DOM container (largest repeated sibling group), URL patterns (sequential numbering like 001.jpg, p1.webp), and position in the DOM.
  • Order pages by DOM order and numeric filename patterns; detect and report duplicates.

Layer 2 — Headless browser rendering (for JavaScript-rendered/lazy-loaded readers). Use Playwright (Chromium) in headless mode to load the page, auto-scroll to trigger lazy loading, wait for network idle, and capture both the rendered DOM and image network responses. Apply the same scoring/filtering logic as Layer 1. Respect timeouts and limit resource use (block fonts/ads/trackers to save bandwidth).

Layer 3 — Gemini-assisted extraction (ambiguity resolver). When heuristics return ambiguous or low-confidence results, send a trimmed list of candidate image URLs with their context (DOM path, dimensions, alt text, position) — and optionally a few thumbnails — to Gemini and ask it to select which images are the chapter's pages and in what order. Output must be validated structured JSON.

Layer 4 — Manual fallback. If the above fail (login-required pages, protected readers, unsupported formats), the UI offers: multi-image upload, ZIP/CBZ upload, PDF upload (render pages to images), or pasting a list of direct image URLs. This guarantees the product works for every source.

Cross-cutting requirements for FR-1:

  • Page Review step is mandatory before any AI call: show detected pages as thumbnails with a confidence indicator; allow delete, reorder, and add. This prevents wasting free-tier quota on wrong images.
  • Report which layer succeeded (useful for debugging and future adapter creation).
  • SSRF protection: only http/https; resolve DNS and block private, loopback, link-local, and metadata IP ranges; limit redirects, response size, and download time.
  • Do not attempt to bypass logins, paywalls, DRM, CAPTCHAs, or other access controls. If detected, stop and offer the manual fallback with a clear message.
  • Throttle requests per host, retry with exponential backoff, and cache downloaded pages.
  • Extract metadata (manga title, chapter number) when available from page title, og: tags, JSON-LD, or Gemini inference; the user can edit it.

FR-2 AI Page Analysis (Gemini Vision)

For each page, call Gemini with the image and request structured JSON output (use the API's response-schema feature). For every text region return:

{
  "page_language": "ja",
  "regions": [
    {
      "id": 1,
      "type": "dialogue | narration | thought | sfx | sign | other",
      "bbox": [ymin, xmin, ymax, xmax],
      "source_text": "original text exactly as written",
      "speaker": "character name or null",
      "reading_order": 1,
      "is_vertical_text": true
    }
  ]
}
  • bbox uses Gemini's normalized 0–1000 convention; the backend converts to pixels.
  • Reading order follows the source convention (right-to-left for Japanese manga, left-to-right for manhwa/manhua/webtoon strips).
  • Very tall webtoon strips must be split into overlapping slices before analysis and re-merged afterwards (deduplicate regions in overlap zones).
  • Validate against a schema; retry up to 2 times on invalid output; otherwise mark the page as failed.

FR-3 Chapter-Level Translation (Context-Aware)

  • After all pages are analyzed, send the whole chapter's regions to Gemini (chunked if necessary) so translation is consistent.
  • Build and persist a chapter glossary (character names, terms, places, honorific decisions) and include it in subsequent requests.
  • Output per region: id_text (Indonesian) and optional note.
  • Style rules (system instruction):
    • Natural, conversational Indonesian, not word-for-word; match each character's personality.
    • Default tone preset = "gaul": modern, casual Indonesian slang as used in everyday chat (e.g., "nggak", "banget", "sih", "dong", "kok", "udah", "gimana"), so dialogue never reads stiff or textbook-like. Choose pronouns per character (gue/lo or aku/kamu) based on personality, age, and relationship, and keep them consistent for the whole chapter. Formal, elderly, or noble characters may use more polite speech, and narration stays neutral and readable. Do not force slang where it does not fit, and do not add vulgarity that is absent from the source.
    • Other presets selectable by user setting: aku/kamu casual, neutral/formal.
    • Do not translate proper nouns; keep common romanization.
    • Honorifics (-san, -kun, -senpai, oppa, etc.): keep or drop by setting.
    • Keep text concise enough to fit speech bubbles.
    • No censorship, no additions, no commentary inside translated text.
    • Preserve punctuation intent (ellipses, "?!").

FR-4 Rendering Translated Pages

Default mode (RENDER_MODE=overlay):

  1. Build padded masks from bbox regions.
  2. Erase original text: sample background color for flat/white bubbles; use OpenCV inpainting for complex backgrounds.
  3. Typeset Indonesian text with Pillow: centered, auto-wrapped, auto-shrinking to fit, open-license comic font (verify license; bundle in repo), black text with optional white stroke over artwork.
  4. Save to data/{chapter_id}/translated/{page}.png, preserving the original dimensions.

Experimental mode (RENDER_MODE=gemini_image, opt-in): Send the page and the (original → Indonesian) replacement list to a Gemini image-editing-capable model with strict instructions to change only the text. Because this may alter artwork or may be unavailable on the free tier, it must include a safeguard: if output dimensions differ or pixel changes outside text regions exceed a threshold, automatically fall back to overlay mode.

FR-5 Background Jobs & Progress

  • POST /api/jobs returns job_id immediately; work runs in the background.
  • Stages: ingesting → awaiting_review → analyzing → translating → rendering → done | failed.
  • Progress via polling or Server-Sent Events (stage, pages done/total, per-page status).
  • Concurrency limit configurable (default conservative, e.g., 2) and a rate-limiter/queue aware of Gemini free-tier limits (requests per minute / per day / tokens); handle HTTP 429 with exponential backoff and resume.
  • A single page failure never fails the whole job; support per-page retry.
  • Cache results by (source + settings) hash.

FR-6 Web Reader

  • Vertical continuous-scroll, fit-to-width, lazy-loaded images.
  • Original/Translated toggle (chapter-wide and per page).
  • Header shows title, chapter, detected language.
  • Mobile-first, swipe/scroll friendly, keyboard shortcuts on desktop, dark mode default.

FR-7 PDF Export

  • "Download PDF" merges translated pages in order using img2pdf.
  • Filename: {manga_title}_ch{number}_ID.pdf. Generated on demand.

FR-8 Settings (per job)

Tone (gaul [default], aku/kamu, neutral), honorifics (keep/drop), SFX (skip/translate), render mode (overlay/gemini_image), Gemini model (default from .env), image quality for AI input (original/downscaled to save quota).

7. Non-Functional Requirements

  • Performance: a 20-page chapter should finish in roughly 5–10 minutes within free-tier limits (rate limiting may dominate).
  • Reliability: all external calls have timeouts, retries, and structured error logs.
  • Security: the app binds to 127.0.0.1 only (local use); API key never reaches the browser; SSRF guard (FR-1); path-traversal protection; upload size/type validation and ZIP-bomb protection; request size limits.
  • Cost control: quota tracking, MAX_PAGES_PER_JOB, image downscaling, caching.
  • Observability: structured logs and per-stage timing; debug view showing detected regions.
  • Portability: documented one-command local run.

8. Legal & Compliance Constraints

  • Personal, non-commercial use only; no public gallery or sharing features.
  • Respect target sites' rate limits and terms; throttle and identify requests politely; never circumvent access controls.
  • All content stays on the user's machine; include a "Delete chapter data" action and optional auto-cleanup (e.g., after 7 days).
  • Show a short in-app notice that users are responsible for complying with copyright law in their jurisdiction.

9. Roadmap & Acceptance Criteria

Phase 1 — Foundation & Core Ingestion. Monorepo scaffold, config, DB, health check, SSRF guard, Layer 1 static extractor with scoring, MangaDex adapter, POST /api/ingest. Accepted when: the extractor returns correctly ordered page lists for every fixture type (static, lazy-load, paginated, webtoon strip), works on public URLs the owner provides, MangaDex works through its adapter, invalid/private URLs are rejected safely, and tests pass.

Phase 2 — Ingestion Hardening. Playwright Layer 2, Gemini-assisted Layer 3, manual upload fallback (images/ZIP/CBZ/PDF), layer orchestrator with confidence reporting. Accepted when: JS-rendered/lazy-loaded reader sites work, and any failing site can still be processed through manual upload.

Phase 3 — Reader & Review UI (no translation yet). Home, review screen (reorder/delete/add), original-page reader, responsive layout. Accepted when: URL → review → read originals works end to end on desktop and mobile.

Phase 4 — Gemini Analysis & Translation. FR-2 and FR-3 with structured output, webtoon slicing, glossary, retries, rate limiter, mocked-API tests. Accepted when: a sample chapter yields validated regions and consistent Indonesian translations within free-tier limits.

Phase 5 — Rendering. Overlay mode (mask, erase, typeset) and region debug view. Accepted when: Indonesian text fits inside ≥90% of standard dialogue bubbles and output dimensions match originals.

Phase 6 — Jobs, Progress, Toggle, PDF. Background runner, progress (polling/SSE), per-page retry, Original/Translated toggle, PDF export, caching. Accepted when: hands-off flow works: paste link → review → live progress → read → download PDF.

Phase 7 — Polish. Settings drawer, experimental gemini_image mode with fallback, cleanup action, Docker, README, error-message polish. Accepted when: all FR items are met and a new developer can run the project in under 10 minutes.

10. Success Metrics

  • ≥85% of sampled translated lines judged natural and understandable.
  • Page-level success rate ≥95%.
  • Automatic ingestion (layers 0–3) succeeds for ≥80% of public sites the owner tries; the remainder succeed via manual fallback (100% coverage).
